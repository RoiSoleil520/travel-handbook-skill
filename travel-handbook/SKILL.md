# 旅行手册网页

将自然语言攻略整理成数据，再用内置模板生成网页。沿用模板的样式与交互，不重新设计页面，不让用户填写大型配置表。

## 工作流程

1. 读取用户给出的攻略、文件或已有对话，提取目的地、出发日期、同行人及每天安排。真实出行缺少目的地/城市或起始日期时才简短追问；其余缺失内容写“待确认”或留空。没有明确日期的真实出行，不擅自指定日期。
2. 阅读 [数据格式](references/data-format.md)，将信息写入工作目录中的 `trip.json`。基础信息使用 `title`、`startDate`、`timezone`、`travelers`、`days`；嵌套结构和可选功能按数据格式填写。标题可从目的地和天数生成，时区使用目的地对应的 IANA 名称，每日日期可从起始日期逐日派生。整理已有攻略时保持原有每日顺序；用户没有给时间时留空，使用 `label: "时间待定"`，不擅自添加活动、时间、价格、航班号或已购状态。按下方规则填写 `theme` 与 `mapProvider`。
3. 用户要求新写攻略或演示行程时，可以编排建议路线，但把建议、示例日期与已确认订单区分清楚；真实出行日期仍需用户确认。公开可核实的门票、交通等价格直接填写，不因用户未预订而统一写“待确认”：注明币种、每人/每车等单位、适用人群、查询日期和包含项目，基础费用与可选项目分开，套票已含费用不重复相加。优先核对政府、景区或运营方的现行价目表；未选商家或无法核实的金额继续留待确认。公开价格不代表已购票，不改变订单状态。引用公开资料时，将可访问的来源链接放入 `sections.overview` 或 `sections.budget`，无法读取的页面不作为已核实来源。完整云南示例仅展示模板用法，不代表实时票价、预约或真实订单。
4. 有图片时，优先使用用户提供且可分享的文件；图片路径填写 `assets/custom/文件名`。没有图片时使用模板占位图，并保留“示意”说明。来源或授权要求署名时保留署名。不要复制私人订单、原攻略 PDF、登录凭据或其他无关数据。
5. 从本 skill 所在目录执行生成命令，输入和输出路径换成实际工作目录路径。输出使用新目录，避免覆盖用户已有网页：

   ```sh
   node scripts/build.mjs --input <trip.json> --output <新目录>
   ```

   自带图片时增加参数，`--assets` 指向包含上述图片文件的目录：

   ```sh
   node scripts/build.mjs --input <trip.json> --output <新目录> --assets <图片目录>
   ```

6. 执行 `node tests/check.mjs`。启动本地静态服务预览输出目录，检查封面、日期切换、每日时间线、景点详情与返回、地图/复制地点、待办保存、配色实时切换及刷新后保留选择，并查看手机/桌面布局；只有数据包含相应内容时才检查角色切换、备选方案、飞机/高铁/自驾卡片与计划倒计时等可选交互。分别查看同行人的专属交通和共同行程，确认“交通住宿”和“交通接送”中的资料完整。可选浏览器自动检查需要 Playwright。
7. 交付完整输出目录、预览方式及尚待确认的信息。需要分享这个 skill 时，交付整个 `travel-handbook` 目录，不单独交付 `SKILL.md`。用户未要求时不安装到全局、不发布网站。

## 选择配色

用户未指定时使用 `green`（苔原绿）。用户明确要求春季/粉色用 `pink`（春樱粉）；夏季/海边配色用 `summer`（夏日海盐）；秋季用 `autumn`（秋日杏茶）；冬季用 `winter`（冬日雾蓝）；新年/节日用 `holiday`（节日朱砂）；紫色用 `purple`（暮山紫）；暗色用 `dark`（午夜深蓝）。以用户明确的配色要求为准，不仅因目的地在海边、出发日期处于某季节或系统开启深色模式就换主题。只在原 JSON 顶层添加如 `"theme": "pink"`，其余数据保持原样。

封面右上“配色”和旅行工具/桌面侧栏“旅行配色”可实时切换；弹窗仅配色选项区滚动，标题、提示和底部“确定”按钮保持可见，点击“确定”收起弹窗。本机按旅行 ID 保存的选择优先于 JSON 默认主题，再回退到绿色。四季/节日只表示配色，不调整布局、日期或行程，用户照片保持原色。

## 选择地图

按地图所指地点的实际区域填写 `mapProvider`，只接受 `amap`（中国内地高德）或 `google`（国外 Google Maps）；不要按浏览器语言、设备时区或页面时钟判断。可在整程顶层、day、event，以及 `place`、`hotel`、`transfer`、`drive`、`stay`、`flight.depart` / `flight.arrival`、`train.depart` / `train.arrival` 局部覆盖。省略时继承上级；day、event、航班或高铁端点若明确给出当地 `zone`，则先按当地时区推断：`Asia/Shanghai`、`Asia/Urumqi` 及其 IANA 别名为高德，其他为 Google；顶层按 `timezone` 推断。`place`、`hotel`、`transfer`、`drive`、`stay` 不增加 `zone` 字段，仅覆盖地图服务或继承上级。

跨境航班分别配置起降端的地点、`zone` 和地图服务，不把整趟行程统一设成 Google。国内搜索词优先写中文正式名加城市，国外使用当地名/英文名加城市；地点未知就保留待确认，不伪造精确地点。高德名称搜索不需坐标；国内接送仅有名称时保留“起点地图/终点地图”两个入口，不编造坐标、不宣称已生成路线。国外接送保留 Google 路线入口，无需添加 SDK 或 API Key。

## 按同行人整理交通

飞机、高铁、自驾卡片统一沿用航班卡的深色样式，并跟随旅行配色。飞机显示计划起飞倒计时，高铁显示计划发车倒计时；高铁发车后按时刻表显示计划已发车或计划已抵达，均非实时运行状态。自驾只显示安排与预计用时，不增加倒计时。

- 飞机用事件内的 `flight`，保留航空公司、航班号、乘机人、机场代码、航站楼、起降日期与当地时间、费用和确认状态。沿用内置深色航班卡及计划倒计时。
- 高铁用 `train`，整理车次、乘车人、出发/抵达站及当地时间、席别、车厢、每人的座位、检票口、费用与状态。时长由起止时间计算，不手写冲突时长；未知座位或检票口留空或待确认，临时变更以车票及车站显示为准。
- 自驾用 `drive`，整理起终点、同行人、车辆和预计用时；租车时再补取车时间与取车点，自有车辆不强制填写。`event.time` 是计划出发时间，`pickupTime` 是取车时间，两者分开。只有估计用时而没有确认抵达时刻时，不编造事件 `end`。
- 不同人的交通分别建事件，通过 `roles` 筛选；共同行程不填 `roles`。需要“全体同行”视图时，在顶层角色中增加 `all`，每个专属事件明确包含 `all` 和该组 ID，例如 `["all","rail"]`。姓名仅供展示，不是登录身份或访问权限；不要把不同人的订单做成同一订单的交通模式切换。
- 真实航班/列车的班次或时间未知时，用普通待定事件，确认后再补完整卡片；跨日与跨时区按各端点日期和当地时区填写。只有用户明确需要演示假数据时才可编排班次、座位等，并在事件及卡片状态显著写“演示数据 · 未预订”，费用注明虚构且未支付。
- 天气备选会替换整天时间线，要保留各组抵达、接送和入住。可用普通事件说明“沿用原交通安排”，飞机/高铁指向“交通住宿”，自驾/接送指向“交通接送”，不重复创建同一订单。

## 模板与数据边界

- 保留所选内置配色、摄影封面、日期条、时间线卡片、手机底部旅行工具、桌面侧栏以及原有键盘与触屏交互。
- 行程时间按活动所在地显示；预览时间应有清晰提示，交通倒计时只表示计划时间，不表示实时运行状态。
- 航班、铁路、租车、酒店、接送和预约的购买/确认状态必须来自用户提供的信息；未知状态标记待确认，演示数据不可写成真实已购。
- 待办与偏好保存在当前浏览器。离线功能需通过 HTTPS 或本地服务打开，并首次联网加载；地图等外部服务仍需网络。
- 本模板不内置账号鉴权和多人云同步。输出是明文静态文件，本机保存也不等于加密。交付前检查是否含用户不希望公开的个人或订单信息。
- 脚本和模板均相对本 skill 目录定位。不要写入作者机器的绝对路径，或把另一次旅程的数据带入新页面。
